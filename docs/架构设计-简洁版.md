# 三维扫描仪软件架构设计

> **对象**：双目激光扫描仪（纯标记点 / 标记点+激光 两模式）。
> **主线**：围绕「**功能 · 性能 · 安全**」三角，简洁讲清要做什么、怎么分模块、**为什么这样设计**。完整 ADR 与多视图见 `框架整体-优化版.md`。

## 2. 模块划分

### 2.1 5 层架构（单向依赖）
```
 UI   →   Workflow   →   Service ∥ Algorithm   →   Data   →   HAL
接入      编排          状态/业务  ∥  纯计算       数据      硬件
```

### 2.2 三个关键设计选择（为什么这样分）
- **为什么分 5 层且单向依赖**：界面、流程、状态、算法、数据、硬件是六个**变化速率不同**的轴。分层让它们各自演进互不牵连；强制单向依赖防架构腐化。
- **为什么 Service 与 Algorithm 并列、Algorithm 纯函数化**：算法改动最频繁、业务状态改动最少。并列让算法被标定/扫描/后处理多工作流**复用**而不耦合业务；纯函数化（无跨帧状态）使其可独立单测、可随时替换。
- **为什么 Data 拥有 Sink（依赖倒置）**：若 HAL 反向依赖 Data，硬件层就被业务绑死，无法独立测试/换平台/故障隔离。改成 Data 定义抽象 Sink 注入 HAL，HAL 只管"推数据"，不感知 Data 存在。

## 3. 模块级交互与处理

### 3.1 交互机制（通信三分）
| 边界 | 机制 | 为什么 |
|---|---|---|
| 控制/通知（按键/状态/故障/急停/光源） | **EventBus**（不携带载荷） | 解耦可换平台；无载荷避免热点 |
| 高频数据（帧/点云流） | **共享内存 Sink 回填** | 零拷贝支撑 180fps |
| Workflow → Algorithm | **直接同步调用** | 纯函数无状态，无队列延迟 |
| UI → Data 点云 | **只读快照直读**（特例） | 渲染级频率免通知往返 |

### 3.2 性能处理（为什么这样能快）
- **数据零拷贝**：180fps 若每帧拷贝/序列化，CPU 被吃光 → 帧流走共享内存。
- **点云前后台双缓冲**：融合写、渲染读若同 buffer 须加锁互阻塞 → 分离无锁。
- **算法同步直调**：算法若走消息队列会排队延迟 → 直接函数调用。
- **GPU 加速**：重建/融合/渲染的重计算 CPU 扛不住 → CUDA + CUDA-GL 零拷贝上屏。
- **跨层直读受控**：渲染要 180fps，走 EventBus 太慢 → 仅 ≥30fps/只读/带版本快照时允许直读。

### 3.3 安全处理（为什么这样才稳）
- **急停**：异步事件总线有排队延迟，急停赌不起 → `publishSync` 同步通道（<100ms）+ 物理硬线并联（<10ms），软件崩了硬线照样停。
- **断电续扫**：长扫描断电不能白扫 → 会话元数据 + 产物实时持久化，重启恢复。
- **故障隔离**：HAL 若强依赖 Data，一处坏全盘崩 → 依赖倒置使单设备失败只上报、不传染。
- **温度补偿**：相机发热致几何微变形会掉精度 → 按温度表切换标定参数，消除热漂移。
- **许可证/审计**：商业授权要绑设备 → 加密狗 + 横切在 UI/SDK 双接入端统一拦截。
- **架构防退化**：单向依赖不校验必被破坏 → CMake 依赖白名单 CI 强制，违规构建失败。

## 附：关键时序
```
急停:   KeyHandler → publishSync(EmergencyStop) → 停采集        (<100ms, 硬线<10ms)
温度:   HardwareMonitor → EventBus(TemperatureUpdate) → 查表换标定
扫描帧: Capture → Preprocess → ┬ MarkerThread(配准 R/T)
                               └ LaserThread(重建, 扫描仪系)
                 → FuseThread(按 R/T 变换到世界系, 体素哈希融合)
                 → RenderThread(直读后台点云快照)
```
