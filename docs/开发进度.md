## 4. 数据流（完整链路）

```
HAL CameraControl (相机回调, 实际帧率)
  ├── ++m_frameCount          → fpsTimer 统计真实采集帧率
  ├── 存 m_latestLeft/Right   → consumerTimer 显示(30fps预览,不抢FrameBuffer)
  └── pushFrame → FrameBuffer → ScanWorkflow 独占消费
                                ↓
                    CaptureStage → PreprocessStage(OpenCV阈值)
                                ↓
                    MarkerStage(CCL→Zernike→Ellipse→Match→Reconstruct)
                                ↓
                    FuseStage(laser_cloud_fuse_cpu → 体素融合)
                                ↓
                    PointCloudBuffer (双缓冲+版本快照)
                                ↓
                    UI OSGWidget (loadFromPointCloudBuffer, 500ms刷新)

HardwareMonitor(1s) → DeviceStateCache → UI 系统信息面板
StateMachine → EventBus → StateChanged
```

## 8. 调试记录

### 8.1 帧率问题（64fps 上限）

**现象**: 相机帧率固定在 ~64fps，设置 freq=100/190 无效。

**排查过程**:
1. 降低曝光时间 → 无效（硬件触发模式下帧率由 MCU 触发频率决定）
2. 切自由采集模式(TriggerMode=Off) → 仍 64fps
3. 降分辨率 1024×768 → 仍 64fps（排除 USB 带宽瓶颈）
4. 解除 AcquisitionFrameRateEnable → 仍 64fps

**结论**: 64fps 是相机 CMOS 传感器读出速度的物理极限（大恒 Galaxy 系列相机），与软件无关。实际产品扫描使用固定 2048×1536 @ 64fps。

**帧率统计修正**:
- 原设计: m_frameCount 在 consumerTimer(33ms) 中递增 → 受显示频率限制
- 修正后: m_frameCount 在相机 SDK 回调中递增 → 反映真实采集帧率
- 显示定时器: 固定 10fps 从 FrameBuffer 取最新帧，不干扰采集

### 8.2 扫描崩溃（0xC0000005 访问冲突）

**现象**: 开始扫描后约 60 帧崩溃，报 vcruntime140.dll 访问冲突。

**排查过程**:

**阶段1 — 排除相机管线**:
- 禁用 ScanWorkflow，只跑相机+显示 → 不崩溃
- 结论: 崩溃在 ScanWorkflow 内部

**阶段2 — 逐步加回处理阶段**:
- 只取帧不处理 → 稳定
- 加 PreprocessStage(adaptiveThreshold) → 稳定
- 加 MarkerStage(Zernike→Ellipse→Match) → 稳定
- 加 FuseStage(laser_cloud_fuse_cpu) → 稳定
- 全管线恢复 → 稳定

**根因1 — 算子每帧创建/销毁**:
```
改前: 每帧 calib::ZernikeEdgeCPU zernikeOp; → new pImpl → Execute → delete pImpl
      60帧后内存碎片化 → 访问已释放内存 → 崩溃
改后: 成员变量 std::unique_ptr<calib::ZernikeEdgeCPU> zernikeOp_ → 构造一次复用
```

**根因2 — 相机回调线程竞争**:
```
改前: 左右两个 SDK 线程同时进入 tryDeliver() → 同时 clone 同一块 cv::Mat → 访问冲突
      每个 event handler 有自己的 mutex → 不互斥
改后: 共享 CameraControl::m_bufferMutex → 写入和 clone 互斥
      DoOnImageCaptured 局部处理后再加锁写入缓冲区
```

**修复措施**:
1. 算子对象改为成员变量，构造时创建一次，所有帧复用
2. tryDeliver 使用 CameraControl 共享锁（m_bufferMutex）
3. DoOnImageCaptured 局部处理后再加锁 swap 到缓冲区
4. 全管线 try-catch 保护

### 8.3 OpenCV Debug 链接问题

**现象**: Debug 模式编译通过但链接失败，12 个 OpenCV 符号未解析。

**排查过程**:
1. dumpbin 检查 .lib 文件 → 符号存在
2. 对比 mangling → Debug 库有 `debug_build_guard` 命名空间，我们的代码没有
3. 检查 cvdef.h → 条件: `defined(_MSC_VER) && (defined(DEBUG) || defined(_DEBUG))`
4. 确认项目设置有 `_DEBUG` → 但 guard 未激活
5. 手动编译测试 → `_DEBUG` 能激活 guard
6. 通过 CMake 构建则不激活（原因不明）

**解决方案**: `add_compile_definitions($<$<CONFIG:Debug>:DEBUG>)`
显式定义 `DEBUG`（非 `_DEBUG`），强制激活 OpenCV debug_build_guard。

### 8.4 CMake 3.31 + CUDA 12.6 + VS2022 兼容性

**现象**: CUDA .cu 文件编译失败，nvcc 报 "A single input file is required"。

**根因**: CMake 3.31 为 VS 项目自动生成 `<WarningLevel>Level4</WarningLevel>`、`<MultiProcessorCompilation>true</MultiProcessorCompilation>`、`<EnableEnhancedInstructionSet>SSE2</EnableEnhancedInstructionSet>`。VS CUDA 12.6 targets 读取这些属性并翻译为 nvcc 参数 `/W4 /MP /arch:SSE2`，但 nvcc 不认识这些 MSVC 选项。

**对比**: JEAMMWARE260705 项目（用旧版 CMake 配置）的 vcxproj 没有这些属性。

**解决方案**: `build_cuda.bat` 脚本在 cmake configure 后、build 前修补 vcxproj，移除 CUDA AdditionalOptions 中的 `/W4 /MP /arch:SSE2`。

## 7. 关键设计决策

| 决策 | 理由 |
|------|------|
| Data层唯一所有者 | 上层经窄接口读写；每对象仅一个★写者 |
| UI层全局只读 | 绝无C/U/D；渲染走直读快照(ADR7.8) |
| Algorithm层零数据权限 | 纯函数叶子；调用方负责读写Data |
| HAL经Sink回填 | 依赖倒置：Data定义IFrameSink，HAL推数据不感知Data |
| AppContext中央装配 | 创建并拥有全部对象，注入WorkflowContext，统一生命周期 |
| 显示与处理分离 | 相机回调存最新帧给UI显示，FrameBuffer仅供Workflow处理 |
| 帧率统计在回调中 | m_frameCount在相机回调递增，反映真实采集帧率 |
| 算子对象复用 | 成员变量构造一次，避免每帧创建/销毁导致内存碎片 |
| 相机回调共享锁 | m_bufferMutex 保护左右SDK线程的缓冲区读写互斥 |
