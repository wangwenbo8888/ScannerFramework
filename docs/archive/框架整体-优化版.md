## 2. 质量属性驱动（架构的第一性驱动力）

> 原文档无质量属性。架构的存在是为满足质量属性；没有它，所有结构选择都失去理由。

### 2.1 质量属性效用树（ATAM 式）

| 业务价值 | 质量属性 | ASR 场景 | 度量（响应/阈值） | 优先级 | 驱动的结构决策 |
|---|---|---|---|---|---|
| 实时扫描 | 性能 | 激光链连续输出 | ≥180 fps；端到端延迟 50–100ms | H | ADR-3 通信机制、§6 线程拓扑 |
| 精度 | 精度 | 单幅激光精度 | 0.01mm/单幅 | H | ADR-2 算法纯函数化 |
| 安全 | 实时性 | 急停硬实时 | publishSync 阈值 100ms；硬线<10ms | H | ADR-3 Critical 通道 |
| 连续作业 | 可靠性 | 断电续扫 | 崩溃后可恢复上次会话 | M | 会话产物持久化 |
| 连续作业 | 可靠性 | 通讯故障隔离 | 单设备掉线不拖垮全局 | M | ADR-4 依赖倒置、故障隔离 |
| 多平台 | 可移植性 | Win/Jetson 双平台 | 编译时多态，无运行时分叉 | M | HAL 平台抽象 |
| 长期演进 | 可修改性 | 新增算子 | 仅加文件，不动框架 | H | 算子三元组契约 |
| 长期演进 | 可修改性 | 新增扫描模式 | 第四模式（如多相机融合）<2 周 | M | ADR-8、§10 扩展点 |
| 交付 | 可测试性 | 算子独立可测 | 三元组+Result，无副作用 | M | ADR-2 |
| 交付 | 安全性 | 许可证/审计 | 加密狗绑定；操作可审计 | M | §4 拆分（横切） |

> **可追溯**：每条 ASR → 度量 → 结构决策 → §3 ADR → §4 组件，构成闭环（见 §12 矩阵）。

## 3. 关键架构决策（ADR）

> 原文档的决策是"断言"或"待复审"。本节给每条顶层决策补**背景/备选/权衡/后果**。

### ADR-1 · 采用 5 层分层架构（UI/Workflow/Service∥Algorithm/Data/HAL）
- **背景**: 需同时满足实时流水线(性能)、双平台移植(可移植)、长期增量演进(可修改)。
- **备选**: ① 微内核+插件（扩展性强但实时调度弱）；② 六边形/端口适配（领域隔离好但流水线编排不顺）；③ 单层管线（性能最优但演进差）。
- **权衡**: 分层牺牲少量跨层调用开销，换取清晰依赖方向、可独立测试、可按层切片落地。
- **后果**: 必须强制单向依赖（ADR-6），否则退化；引入"性能特例"机制（ADR-3、§5 例外准则）。

### ADR-2 · Service ∥ Algorithm 并列且互不依赖，Algorithm 纯函数化
- **背景**: 算法高频变更、需独立单测；状态/业务低频但全局。
- **备选**: Algorithm 置于 Service 之下（Service 调 Algorithm）。
- **权衡**: 并列使算法可被标定/扫描/后处理多 workflow 复用而不引入对 Service 的依赖；代价是 Workflow 必须显式编排数据↔算法。
- **后果**: Algorithm 不持有跨帧状态（融合哈希归 Data）；Result 携带 status 不抛异常。

### ADR-3 · 通信机制三分（控制→EventBus / 数据→共享内存 / 算法→直接调用）
- **背景**: 原文档隐含 4 种通信却未规定边界归属。
- **决策**:
  - **控制/通知**（按键/状态/故障/急停/光源/指示灯）→ EventBus，Critical 用 `publishSync`。
  - **高频数据**（帧/点云流）→ Data 层共享内存/双缓冲。
  - **算法调用** → Workflow 经 WorkflowContext 直接同步调用。
- **后果**: 急停走 Critical 同步通道满足硬实时（ASR）；EventBus 不携带载荷，避免热点。

### ADR-4 · 依赖倒置：Data 拥有 Sink，HAL 仅依赖抽象回填
- **背景**: 解耦 HAL↔Data，使 HAL 可独立测试/换平台。
- **决策**: `IFrameSink`/`IDeviceStateSink` 由 Data 层拥有并注入 HAL；HAL 产出推给 Sink，不反向依赖 Data。
- **后果**: 设备掉线可隔离（ASR 可靠性）；新增设备只需实现 Sink 推送（见 §10 扩展点）。

### ADR-5 · 契约稳定性分级与版本化
- **背景**: SDK 对外 + 设备接入需稳定契约。
- **决策**: 契约三档——`@Stable`（SDK/设备接口，语义化版本）、`@Internal`（层间契约，同 major 可变）、`@Experimental`（算子）。framework/ 桩头加版本宏。
- **后果**: 新增设备走 `@Stable`，保证第三方设备可接入。

### ADR-6 · 依赖规则机器校验（fitness function）
- **背景**: "单向依赖"无校验必退化（现状 Scheduler/Watchdog 已退化成空类桩）。
- **决策**: CMake 目标级依赖白名单 + 头文件 include 规则自动检查（CI 跑）。违规即构建失败。
- **后果**: 架构不可被无声违反（ASR 长期演进）。

### ADR-7 · 模块边界规则：单模块主层 + 受限跨层（决断原 C1）
- **背景**: 模块8 跨 4 层 = 上帝模块。根因是"无跨层上限规则"。
- **决策**:
  - 模块有且仅有一个**主层**；跨层≤2 层，且必须显式标注跨层契约。
  - **模块8 拆分**：许可证/激活→横切；设备状态监控→Service；硬件驱动→HAL；设备 UI→UI。主层定 **Service**。
- **后果**: 消除上帝模块；CMake 链不再跨全 5 层。

### ADR-8 · 扩展点机制（决断原 C3 侧边设施归属）
- **背景**: "受控演进"要求显式扩展点。
- **决策**: 四类扩展点——① 新设备（实现 `IScannerCamera` + Sink）；② 新算子（三元组 + 注册）；③ 新工作流（IWorkflow + Stage 组合）；④ 新平台（HAL 平台实现）。EventBus/GpuRuntime/Scheduler/Watchdog 归属：**EventBus→infra（跨层共用）；GpuRuntime→infra；Scheduler/Watchdog→Workflow 持有**。

## 5. 边界与依赖规则（可机器校验）

### 5.1 依赖方向白名单（ADR-6）
```
UI      → Workflow, Service, Data(特例), EventBus(订阅)
SDK     → 各层(@Stable 门面)
Workflow→ Service, Algorithm, Data, EventBus
Service → Data, EventBus              (不依赖 Algorithm, 不直调 HAL)
Algorithm → (无)                       (纯叶子, 直接用三方库)
Data    → (无业务依赖)                 (拥有 Sink, 注入 HAL)
HAL     → Sink 抽象(依赖倒置)          (不依赖 Data 实现)
infra   → 被各层依赖(EventBus/GpuRuntime/Scheduler)
横切    → 被各层依赖
```
**禁止**: 反向依赖、跨层跳级（如 UI→Algorithm）、Service↔Algorithm 互依。
**校验**: CMake `target_link_libraries` 白名单 + 头文件 include 检查脚本，CI 强制。

### 5.2 边界通信机制矩阵
| 边界 | 机制 | 理由 |
|---|---|---|
| Service→HAL 控制 | EventBus(LightControl/LedControl) | 解耦 + 可换平台 |
| 急停 | EventBus `publishSync`(Critical) | 硬实时(ASR) |
| HAL→Data 帧流 | Sink 回填(共享内存) | 零拷贝高频(180fps) |
| Workflow→Algorithm | 直接同步调用 | 纯函数，无热点 |
| Data→UI 点云 | 直读(特例) | 180fps 渲染(见 5.3) |
| 跨层状态通知 | EventBus(StateChanged 等) | 不携带载荷 |

### 5.3 性能特例准则（原文档无准则）
允许跨层直读（如 UI→Data 点云）**当且仅当**：
1. 频率≥渲染级（≥30fps）；
2. 只读；
3. 经 Data 层提供的只读快照接口（带版本号，无锁或读写锁）；
4. 在 ADR 登记。
**不满足则必须走 EventBus/Workflow。**

### 5.4 数据 SSOT（单一事实源）
| 数据 | Owner(SSOT) | 消费方(只读/cache) |
|---|---|---|
| 标定参数(含温度表) | Data·CalibrationData | 各算法线程(只读) |
| 全局点云 | Data·PointCloudBuffer | UI 渲染(只读快照) |
| 设备状态 | Data·DeviceStateCache | UI/Service |
| 会话/产物 | Data·ArtifactStore | 文件 IO |

### 5.5 一致性模型
- 标定参数：读写锁，读多写极少（温度切换）。
- 点云：前后台双缓冲（ADR7.8），渲染读后台快照（最终一致）。

## 6. 运行时/进程视图

### 6.1 线程拓扑
```
CaptureThread(扫描仪帧) ──→ PreprocessThread ──┬─→ MarkerThread(物标记点, 模式1/2)
                                                └─→ LaserThread(激光重建, 扫描仪系)
FuseThread ◀── 按标记点配准并融合到世界系
RenderThread(UI, 直读后台点云快照)
ServiceThread(温度补偿/状态机/会话)
EventBus·DispatchThread(Critical/High/Normal/Low 多队列)
Scheduler/Watchdog(Workflow 持有)
```

### 6.2 关键时序
- **急停**: KeyHandler→`publishSync(EmergencyStop)`→LightDriver 同步停采集（<100ms，硬线<10ms）。
- **温度补偿**: HardwareMonitor→EventBus(TemperatureUpdate)→TempCompensationService→CalibrationData 查表切换（不调 Algorithm）。
- **标记点配准融合**: MarkerThread 输出位姿 R/T，FuseThread 将 LaserThread 的点云(scanner 系)用 R/T 变换并融合到世界系。

## 9. 场景视图（用例穿针）

### 9.1 标记点+激光扫描场景（详写）
```
1. 设备就绪: 扫描仪连接; 相机/激光标定已加载
2. 预扫标志点: MarkerThread 提取被扫物标记点 → 解算初始 R/T
3. 选模式2(标记点+激光): 状态机启动 ScanWorkflow
4. 启动: 扫描仪相机同步采集(MCU 硬触发)
5. 逐帧:
   a. MarkerThread: 扫描仪帧 → mask_extract → 标记点链 → R/T(scanner←world)
   b. LaserThread: 扫描仪帧 → steger → undistort → epipolar_interp
      → laser_reconstruct → 点云(scanner 系)
   c. FuseThread: 按 R/T 将点云变换到世界系 → 体素哈希融合
6. 渲染: RenderThread 直读后台点云快照(世界系)
7. 停止/会话: 会话产物持久化(支持断电续扫)
※ 配准源 = 被扫物标记点
```

### 9.2 其他场景（简表）
| 场景 | 走针 |
|---|---|
| 相机标定 | 25 姿态→标定算子→标定参数 SSOT |
| 扫描(纯标记点模式) | 物标记点链配准，激光链关闭 |
| 急停 | 见 §6.2 |
| 断电续扫 | 会话元数据+产物持久化→重启恢复 |
| 后处理 | GBA→重融合→法线→网格(待建)→STL |
