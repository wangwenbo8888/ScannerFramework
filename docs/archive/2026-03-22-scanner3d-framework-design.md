## 1. 概述

### 1.1 项目目标
设计一个高性能软件框架，用于手持式双目三维多线激光扫描仪，满足以下核心指标：
- **帧率**: 180fps 连续输出
- **精度**: 0.01mm/单幅
- **分辨率**: 0.01mm~2mm
- **点云规模**: 5-10万点/帧
- **延迟**: 50-100ms（采集到融合完成）
- **平台**: Windows 10/11 x64（主），Jetson Orin NX/AGX Orin（兼容）

### 1.2 设计原则
- **速度优先**: 零拷贝数据传输、GPU加速、流水线并行
- **平台兼容**: 硬件抽象层实现编译时多态
- **模块化**: 五层分层架构，单向依赖，职责清晰
- **单一职责**: 每层专注核心职责，算法/数据/设备分离

## 2. 架构设计

### 2.1 整体架构图

采用**五层分层架构 + 事件总线 + 横切关注点**，自下而上依次为硬件抽象层、数据层、[服务层与算法层并行]、工作流层、界面层。

**核心设计原则**：
- **Algorithm层纯函数化**：只做计算，输入参数→输出结果，无副作用，不访问Data层
- **Service层收窄职责**：依赖Data层和EventBus，负责状态管理、参数管理、故障处理、事件路由
- **Workflow层承担编排**：通过WorkflowContext统一访问Service层、Data层、Algorithm层
- **统一事件通信**：Service层与HAL层之间的所有通信（包括紧急操作）统一通过EventBus，不设"特例直接调用"

**DataContext与WorkflowContext职责边界**：
- **DataContext**：专注于Data层数据访问封装，提供类型安全的读写接口，隐藏线程同步细节
- **WorkflowContext**：专注于Workflow完整上下文管理，聚合Service层（状态/参数）、DataContext、Algorithm注册表
- **关系**：WorkflowContext内部使用DataContext，DataContext是WorkflowContext的组成部分之一

### 2.2 各层职责

**第1层 - 硬件抽象层（HAL层）**
- **接口定义**（平台无关）:
  - **相机接口(ICamera)**: 相机通过下位机中继与上位机通讯，每个相机有独立端口
    - 相机1端口: 图像数据接收、参数配置（11个预留指令）、温度/帧率读取
    - 相机2端口: 图像数据接收、参数配置（11个预留指令）、温度/帧率读取
    - **注意**: 相机的硬件触发由IMCU接口控制，ICamera接口不负责触发
  - **下位机接口(IMCU)**: 控制外设、相机硬件触发和同步采集
    - **相机硬件触发**: 控制相机1/相机2的I/O硬触发（同步采集的核心）
    - 激光器控制（17/25条440-450nm蓝色激光线）
    - 补光灯控制（2个450nm LED环形补光灯）
    - 指示灯控制（红/绿状态指示）
    - 按键状态读取
    - 温度传感器读取（骨架温度）
    - 预留指令收发（15个）
  - **CUDA上下文接口(ICudaContext)**: GPU内存管理、Stream管理、设备信息
  - **平台接口(IPlatform)**: 平台类型、CUDA架构、GPU数量
- **纯硬件驱动**（无业务语义）:
  - **指示灯驱动(LedDriver)**: 
    - 只提供setColor(color)，不包含"故障=红色"等业务语义
    - 订阅EventBus的LedControl事件，执行颜色设置
  - **光源驱动(LightDriver)**: 
    - 只提供激光亮度/补光灯亮度设置，不包含采集流程控制
    - 订阅EventBus的LightControl事件，执行光源参数设置
    - 订阅EventBus的EmergencyStop事件，执行紧急停止
  - **硬件监控器(HardwareMonitor)**: 
    - 只读取原始传感器值，不做业务判断（如温度阈值）
    - 周期性发布TemperatureUpdate、FrameRateUpdate等事件到EventBus
- **平台实现**: Windows实现、Jetson实现（编译时多态）
- **依赖**: 无（最底层）
- **设计原则**: 
  - HAL层只做纯硬件操作，不包含任何业务逻辑
  - 业务逻辑（如"故障=红灯"、"温度>60°C是异常"）在Service层实现
  - HAL层通过订阅EventBus事件响应Service层的控制命令

**第2层 - 数据层（Data层）**
- **共享内存池(SharedMemoryPool)**: 环形缓冲区实现，零拷贝图像传输
- **点云缓冲区(PointCloudBuffer)**: 全局点云存储，增量更新，线程安全访问
- **标定数据(CalibrationData)**: 
  - 内参、外参、立体矫正参数、光平面参数
  - 温度-参数映射表（由TempCompensationService触发Algorithm层预计算生成）
  - 当前生效参数（由TempCompensationService触发运行时切换）
- **设备状态缓存(DeviceStateCache)**: 硬件状态缓存（温度、帧率等），由HAL层写入
- **文件IO管理器(FileIOManager)**: 工程文件保存/加载、点云导入导出（PLY/TXT/ASC）、三角网格导出（STL/PLY/OBJ）
- **原始帧存储(RawFrameStorage)**: 缓存未做全局融合前的帧数据（标记点3D、激光点3D），供后处理使用
- **单帧判断模块(FrameDecisionModule)**: 判断当前帧激光点云是否需要保存到原始帧存储
- **GPU内存池(GpuMemoryPool)**: 管理GPU显存的分配、复用和释放，支持零拷贝数据传输
- **依赖**: 无（纯数据管理，不依赖其他业务层）

**温度补偿参数管理说明**:
- 温度补偿参数表的**生成**由TempCompensationService通过WorkflowContext调用Algorithm层完成
- 温度补偿参数的**缓存**由TempCompensationService管理（常用温度区间）
- 温度补偿参数的**查表切换**由TempCompensationService触发CalibrationData执行
- CalibrationData只负责存储，不包含温度补偿的业务逻辑

**死锁预防策略**:

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                          死锁预防策略                                        │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  1. 【锁获取顺序】（全局约定）                                               │
│     CalibrationData → PointCloudBuffer → RawFrameStorage                  │
│     (按此顺序获取锁，不允许反向)                                            │
│                                                                             │
│  2. 【避免嵌套锁】                                                          │
│     · 单个操作只获取一个锁                                                  │
│     · 需要多个资源时使用tryLock或超时机制                                   │
│                                                                             │
│  3. 【读写锁使用场景】                                                      │
│     · PointCloudBuffer: 读频繁(渲染)、写频繁(融合) → rwlock               │
│     · CalibrationData: 读极频繁、写极少 → rwlock                          │
│     · SharedMemoryPool: 环形缓冲，无需锁 → 原子索引                       │
│                                                                             │
│  4. 【无锁设计】                                                            │
│     · SharedMemoryPool: 使用环形缓冲+原子索引，避免锁                      │
│     · GpuMemoryPool: CUDA Stream同步，避免CPU端锁                          │
│     · DeviceStateCache: 原子变量存储温度/帧率                              │
│                                                                             │
│  5. 【线程安全数据结构】                                                    │
│     · 使用线程安全队列（内部已加锁）                                        │
│     · 使用std::atomic进行简单状态同步                                      │
│                                                                             │

**第3层a - 服务层（Service层）[与Algorithm层并行]**
- **职责**: 状态管理、参数管理、故障处理、事件路由
- **状态机(StateMachine)**: 管理系统全局状态，控制工作流切换
- **参数管理(ParameterManager)**: 集中管理相机参数、算法参数、用户设置
- **故障处理(FaultHandler)**: 订阅故障事件，提供故障恢复机制
  - 通过EventBus发布LedControl事件控制指示灯
- **信号分发(SignalDispatcher)**: 管理EventBus订阅，将硬件事件、状态变化路由到订阅者
- **温度补偿服务(TempCompensationService)**: 
  - 订阅EventBus的温度更新事件（由HAL层HardwareStatusReader发布）
  - 判断温度变化是否达到阈值
  - **达到阈值时调用Data层CalibrationData查表切换标定参数**
  - **统一管理温度补偿逻辑**：负责参数表缓存、查表切换、参数验证
- **按键处理(KeyHandler)**: 
  - 订阅EventBus的按键事件（由HAL层发布）
  - 执行对应的业务逻辑（开始/停止扫描、切换工作流等）
  - **紧急停止(组合键)通过EventBus发布EmergencyStop事件**，HAL层LightDriver订阅并立即执行
- **依赖**: 
  - 依赖Data层（参数、状态读写）
  - 依赖EventBus（与HAL层通信）
  - **不直接调用HAL层接口**，所有硬件控制通过EventBus事件发布

**第3层b - 算法层（Algorithm层）[与服务层并行]**
- **职责**: 纯计算，无副作用，输入参数→输出结果
- **设计原则**:
  - 不访问Data层，由Workflow层负责数据的读写
  - 直接使用第三方库（OpenCV、PCL、Open3D、CGAL、Eigen），不经过适配层
- **GPU算法**:
  - 图像预处理、多线激光提取（17/25条）、立体匹配、极线插值、三维重建、光顺处理
- **CPU算法**:
  - 扫描相关：标记点检测、融合、配准、下采样、网格封装、补洞、光顺
  - 标定相关：姿态计算、外参计算、立体矫正计算、光平面标定、温度补偿参数表生成
- **典型接口模式**:
  ```cpp
  // 输入参数，输出结果，无副作用
  Result Algorithm::process(const InputParams& params, const InputData& data);
  ```
- **依赖**: 无（纯函数计算，不依赖任何业务层）

**第4层 - 工作流层（Workflow层）**
- **职责**: 编排Service + Algorithm + Data的协作，管理业务流程生命周期
- **IWorkflow统一接口**: 所有工作流实现统一接口
  ```cpp
  class IWorkflow {
  public:
      virtual void execute() = 0;      // 执行工作流
      virtual void stop() = 0;         // 停止工作流
      virtual void pause() = 0;        // 暂停工作流
      virtual void resume() = 0;       // 恢复工作流
      virtual WorkflowStatus getStatus() = 0;  // 获取状态
  };
  ```
- **WorkflowContext工作流上下文**: 为Workflow提供统一的依赖访问入口，简化Workflow实现
  - `getState()`: 获取系统状态（转发到Service层StateMachine）
  - `getParams()`: 获取参数（转发到Service层ParameterManager）
  - `readFrame()`: 读取帧数据（转发到Data层SharedMemoryPool）
  - `writePointCloud()`: 写入点云（转发到Data层PointCloudBuffer）
  - `readCalibParams()`: 读取标定参数（转发到Data层CalibrationData）
  - `executeAlgorithm(name, input)`: 执行算法（转发到Algorithm层对应算法）
  - `publishProgress(progress)`: 发布进度事件（转发到EventBus）
  - `publishComplete(result)`: 发布完成事件（转发到EventBus）
- **DataContext数据上下文**: 封装对Data层的所有读写操作（详见2.7.20节）
  - WorkflowContext内部使用DataContext访问Data层
  - DataContext职责更加聚焦于数据访问
- **工作流类型**:
  - **PipelineWorkflow**: 实时帧处理，多线程流水线（标定、扫描标记点、扫描点云）
  - **BatchWorkflow**: 离线批量处理（后处理）
  - **SyncWorkflow**: 同步阻塞操作（文件IO）
- **生命周期管理**:
  - 状态: Idle → Running → Paused → Completed / Stopped / Error
  - 由Service层StateMachine控制工作流的启动和停止
  - 支持进度回调和事件发布（WorkflowProgress、WorkflowComplete）
- **Pipeline框架**: 提供可组合的Stage架构，支持串行和并行配置
  - Pipeline容器 + SequentialStage/ParallelStage组合器
  - 可复用的Stage模块（采集、预处理、提取、重建、配准、融合等）
- **业务工作流配置**:
  - 标定工作流: 采集 → 预处理 → 标记点提取 → 姿态计算 → 标定
  - 扫描标记点工作流: 采集 → 预处理 → 标记点提取 → 重建 → 配准
  - 扫描点云工作流: 采集 → 预处理 → [标记点分支 + 激光点分支] → 融合
- **依赖**: WorkflowContext（统一依赖入口，通过WorkflowContext访问Service/Algorithm/Data层）

**关键原则**:
1. **单向依赖**: 上层依赖下层，下层不依赖上层
2. **Service与Algorithm并行**: 两者不互相依赖，由Workflow层编排调用（图中用╔═══╗标注互不依赖）
3. **Algorithm纯函数化**: 输入参数，输出结果，无副作用，不访问Data层
4. **Service主要依赖Data层和EventBus**: 不依赖Algorithm层，温度补偿由TempCompensationService统一管理
5. **数据局部性**: 数据在Data层统一管理，Workflow层通过WorkflowContext（内含DataContext）读写
6. **事件解耦**: 下层通过EventBus发布事件，上层订阅，避免反向依赖
7. **统一EventBus通信原则（无特例）**: 
   - **所有Service→HAL层通信必须通过EventBus**，不设"直接调用特例"
   - 故障指示灯控制: Service层发布LedControl事件，HAL层LedDriver订阅处理
   - 紧急停止: Service层发布EmergencyStop事件（使用publishSync同步发布），HAL层LightDriver订阅处理
   - 光源控制: Service层发布LightControl事件，HAL层LightDriver订阅处理
   - **关键操作使用publishSync**: 保证紧急停止等关键操作实时性（同步执行，无队列延迟）
8. **性能优化特例**: UI层直接读取Data层点云数据是为了180fps渲染性能
9. **IWorkflow统一接口**: 所有工作流实现统一接口，便于状态机管理和扩展
10. **WorkflowContext聚合DataContext**: DataContext作为WorkflowContext的组成部分，专门负责Data层访问
11. **生命周期管理**: 工作流具有完整生命周期（启动/暂停/恢复/停止），由状态机控制

**HAL层纯硬件化原则**:
- HAL层只做纯硬件操作，不包含任何业务语义
- 业务逻辑（如"故障=红灯"、"温度>60°C是异常"）在Service层实现
- HAL层通过订阅EventBus事件响应Service层的控制命令
- 这种设计使HAL层更易于测试和平台移植

**EventBus健康监控机制**:
- **超时检测**: publishSync操作设置超时阈值（默认100ms），超时触发告警
- **队列积压告警**: 各优先级队列长度超过阈值时发布告警事件
- **订阅者状态追踪**: 监控订阅者回调执行时间，异常时记录日志
- **故障隔离**: 单个订阅者异常不影响其他订阅者

### 2.5 模块通信机制

#### 2.5.1 通信类型总览

| 通信类型 | 机制 | 适用场景 | 示例 |
|---------|------|---------|------|
| 同步调用 | 直接接口调用 | 上层调用下层 | 工作流层调用Algorithm层算法 |
| 数据共享 | 共享内存+互斥锁 | 高频数据访问 | 多线程访问全局点云 |
| 事件通知 | EventBus发布订阅 | 下层通知上层 | 硬件故障通知到界面层 |
| 状态同步 | EventBus发布订阅 | 跨层状态更新 | 服务层状态变化通知界面层 |

#### 2.5.2 EventBus事件总线

**设计目标**: 解耦下层与上层的依赖，允许下层通过发布事件通知上层，而不需要直接依赖上层。

**事件优先级机制**:

```
EventPriority枚举:
┌─────────────────────────────────────────────────────────────────────┐
│ 优先级       │ 值  │ 说明                    │ 处理方式            │
├──────────────┼─────┼─────────────────────────┼─────────────────────┤
│ Critical     │ 0   │ 紧急停止、故障          │ publishSync立即执行 │
│ High         │ 1   │ 状态变化、按键          │ 优先队列            │
│ Normal       │ 2   │ 帧就绪、温度更新        │ 普通队列            │
│ Low          │ 3   │ 帧率统计、日志          │ 延迟队列，可合并    │
└─────────────────────────────────────────────────────────────────────┘
```

**事件合并策略**:

| 合并类型 | 适用事件 | 说明 |
|---------|---------|------|
| **Latest** | FrameRateUpdate | 只保留最新值，丢弃旧事件 |
| **Merge** | TemperatureUpdate | 合并相同类型，保留最新数据 |
| **None** | FaultOccurred, StateChanged | 不合并，保证每个事件都处理 |

**EventBus接口设计**:

```
EventBus {
    // 订阅事件
    subscribe(eventType, callback)
    
    // 取消订阅
    unsubscribe(eventType, callback)
    
    // 发布事件（异步，指定优先级）
    publish(event, priority = Normal)
    
    // 发布事件（异步，可合并）
    publishMergeable(event, mergeStrategy)
    
    // 发布事件（异步，只保留最新）
    publishLatest(event)
    
    // 发布事件（同步，立即回调，Critical级别）
    publishSync(event)
}
```

**事件处理线程架构**:

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    EventBus多队列处理架构                                     │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  发布者                    优先级队列                    消费者线程         │
│  ┌─────┐                ┌─────────────┐              ┌─────────────┐       │
│  │ All │ ──────────────→│  Critical   │ ───────────→│  紧急线程   │       │
│  │     │  publishSync   │   Queue     │  最高优先   │  (实时处理) │       │
│  └─────┘                └─────────────┘              └─────────────┘       │
│                                                                             │
│  ┌─────┐                ┌─────────────┐              ┌─────────────┐       │
│  │ All │ ──────────────→│    High     │ ───────────→│  状态线程   │       │
│  │     │  publish(High) │   Queue     │             │  (状态管理) │       │
│  └─────┘                └─────────────┘              └─────────────┘       │
│                                                                             │
│  ┌─────┐                ┌─────────────┐              ┌─────────────┐       │
│  │ All │ ──────────────→│   Normal    │ ───────────→│  通用线程   │       │
│  │     │publish(Normal) │   Queue     │             │  (常规处理) │       │
│  └─────┘                └─────────────┘              └─────────────┘       │
│                                                                             │
│  ┌─────┐                ┌─────────────┐              ┌─────────────┐       │
│  │ All │ ──────────────→│     Low     │ ───────────→│  后台线程   │       │
│  │     │  publish(Low)  │   Queue     │  可合并     │  (延迟处理) │       │

│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

**时序保证**:
1. **同步事件**: `publishSync`立即在调用线程执行，保证顺序，用于Critical级别
2. **优先级顺序**: 高优先级队列优先处理，低优先级可能延迟
3. **事件合并**: 标记为Mergeable/Latest的事件在入队前检查并合并
4. **事件去重**: Latest类型事件只保留最新一条，旧事件被丢弃

```

### 2.7 关键模块详细说明

#### 2.7.1 按键处理模块（KeyHandler）- 服务层

**功能**: 订阅按键事件，执行对应的业务逻辑

**位置**: 服务层

**设计原则**: 所有与HAL层的通信统一通过EventBus，不直接调用HAL层接口

**调用关系**:
```
HAL层(IMCU.getKeyStatus) → EventBus.publish(KeyPressed) → Service层(KeyHandler订阅) → 状态机/工作流层
                                                                    ↓ (紧急停止)
                                                         EventBus.publishSync(EmergencyStop)
                                                                    ↓
                                                         HAL层(LightDriver订阅) → 停止采集
```

**事件订阅**:
- 订阅 `EventType::KeyPressed` 事件
- 事件数据包含: keyCode, keyState (按下/释放/长按)

**按键检测逻辑**（在KeyHandler内部实现）:
- 支持单击、长按检测
- 支持组合键检测
- 按键去抖动处理

**按键事件类型**:
- `KeyEvent::StartStop`: 开始/停止扫描
- `KeyEvent::SwitchMode`: 切换工作流模式
- `KeyEvent::EmergencyStop`: 紧急停止（组合键）
- `KeyEvent::Confirm`: 确认操作

**事件响应**:
| 按键事件 | 响应动作 | HAL层通信方式 |
|---------|---------|--------------|
| StartStop | 切换扫描状态（开始↔停止） | 通过EventBus发布LightControl事件 |
| SwitchMode | 循环切换工作流 | 无需HAL层通信 |
| EmergencyStop | 立即停止所有操作 | 通过EventBus发布EmergencyStop事件 |
| Confirm | 确认当前操作 | 无需HAL层通信 |

**接口定义**:
```cpp
class KeyHandler {
public:
    void initialize();  // 订阅EventBus按键事件
    
private:
    EventBus* eventBus_;  // 只依赖EventBus，不依赖HAL层
    
    void onKeyPressed(const KeyEvent& event);
    
    // 通过EventBus发布紧急停止事件
    void emergencyStop() {
        Event e;
        e.type = EventType::EmergencyStop;
        e.data["reason"] = "user_key_press";
        eventBus_->publishSync(e);  // 同步发布，立即执行
    }
    
    // 通过EventBus发布光源控制事件
    void startAcquisition() {
        Event e;
        e.type = EventType::LightControl;
        e.data["action"] = "start";
        eventBus_->publish(e, EventPriority::High);
    }
    
    void stopAcquisition() {
        Event e;
        e.type = EventType::LightControl;
        e.data["action"] = "stop";
        eventBus_->publish(e, EventPriority::High);
    }
};
```

#### 2.7.1a 故障处理模块（FaultHandler）- 服务层

**功能**: 订阅故障事件，执行故障处理和恢复逻辑

**位置**: 服务层

#### 2.7.2 硬件监控器（HardwareMonitor）- HAL层

**功能**: 读取原始硬件状态值

**位置**: 硬件抽象层（HAL层，纯硬件驱动）

**设计原则**: 只读取原始值，不做业务判断（如温度阈值判断）

**调用关系**:
```
HAL层(HardwareMonitor) → HAL层(IMCU/ICamera) → 读取硬件状态 → 返回原始值
                                                    ↓
                                Service层(HardwareMonitorService)订阅并处理
```

**监控项目**:
- 相机1/2温度（原始值）
- 骨架温度（原始值）
- 帧率统计（原始值）

**接口定义**:

```
HardwareMonitor {
    // 初始化
    initialize(IMCU, ICamera1, ICamera2)
    
    // 读取原始值（不包含业务判断）
    float getFrameTemperature()    // 骨架温度
    float getCamera1Temperature()  // 相机1温度
    float getCamera2Temperature()  // 相机2温度
    float getCamera1FrameRate()    // 相机1帧率
    float getCamera2FrameRate()    // 相机2帧率

    void publishHardwareStatus()
}
```

**与Service层的关系**:
- HardwareMonitor只读取和发布原始数据
- 业务判断（如温度>60°C是异常）在Service层HardwareMonitorService中实现

#### 2.7.2a 硬件监控服务（HardwareMonitorService）- 服务层

**功能**: 订阅硬件状态事件，执行业务判断和处理

**位置**: 服务层

**业务逻辑**:
- 温度阈值判断（可配置阈值，如60°C）
- 帧率异常检测（如低于150fps）
- 发布业务事件（如TemperatureWarning）

**接口定义**:

```

    // 配置
    float tempWarningThreshold = 60.0     // 温度警告阈值
    float tempCriticalThreshold = 80.0    // 温度严重阈值
    float fpsWarningThreshold = 150.0     // 帧率警告阈值
    
    // 订阅HAL层事件
    void onHardwareStatus(HardwareStatusEvent event) {
        // 业务判断
        if (event.frameTemp > tempWarningThreshold) {
            eventBus.publish(TemperatureWarning{event.frameTemp});
        }
        if (event.fps < fpsWarningThreshold) {
            eventBus.publish(FrameRateWarning{event.fps});
        }
    }
}
```

#### 2.7.10 温度补偿服务（TempCompensationService）- 服务层

**功能**: 统一管理温度补偿逻辑，包括参数表缓存、查表切换、参数验证

**位置**: 服务层

**设计原则**: **统一管理温度补偿全流程，包括预计算触发、参数表缓存、运行时查表切换**

**职责范围**:

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                  TempCompensationService 统一管理职责                         │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  【标定阶段】触发预计算                                                       │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │  1. 标定工作流完成时，调用TempCompensationService.onCalibrationComplete()│
│  │  2. Service通过WorkflowContext调用Algorithm层TempCompensator生成参数表│
│  │  3. Service将生成的参数表写入Data层CalibrationData                    │   │
│  │  4. Service建立温度索引，缓存常用温度参数                             │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
│  【运行阶段】查表切换                                                         │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │  1. 订阅HAL层发布的TemperatureUpdate事件                              │   │
│  │  2. 判断温度变化是否超过阈值                                          │   │
│  │  3. 从缓存或CalibrationData中查找最接近的参数                         │   │
│  │  4. 验证参数有效性                                                   │   │
│  │  5. 触发CalibrationData切换到对应温度的标定参数                       │   │
│  │  6. 发布CalibrationUpdated事件通知相关模块                            │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
│  【参数表缓存】                                                              │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │  · 缓存常用温度区间的参数（如20°C±10°C）                              │   │
│  │  · 减少对Data层的频繁访问                                            │   │
│  │  · 缓存失效时自动从CalibrationData重新加载                           │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

**工作原理**:
1. **订阅温度事件**: 订阅HAL层HardwareMonitor发布的`TemperatureUpdate`事件
2. **阈值判断**: 比较当前温度与当前使用的标定参数对应温度，判断差值是否超过阈值
3. **查表切换**: 达到阈值时，从缓存或Data层CalibrationData的温度-参数映射表中查找最接近的参数并切换
4. **参数验证**: 验证切换后的参数数值稳定性
5. **事件通知**: 发布CalibrationUpdated事件通知Workflow层和UI层

**输入**:
- 相机1温度（来自HAL层HardwareMonitor）
- 相机2温度（来自HAL层HardwareMonitor）
- 骨架温度（来自HAL层HardwareMonitor）

**输出**:
- 触发Data层CalibrationData切换到对应温度的标定参数
- 发布CalibrationUpdated事件

**配置参数**:
| 参数 | 说明 | 默认值 |
|------|------|--------|
| `monitorInterval` | 温度监控周期(ms) | 1000 |
| `tempThreshold` | 温度变化阈值(°C) | 2.0 |
| `compensationEnabled` | 是否启用温度补偿 | true |
| `cacheSize` | 参数缓存条目数 | 10 |

**调用关系**:
```
【标定阶段】
Workflow层(标定完成) → Service层(TempCompensationService.onCalibrationComplete)
                                     ↓
                          WorkflowContext.executeAlgorithm("TempCompensator")
                                     ↓
                          Algorithm层(TempCompensator生成参数表)
                                     ↓
                          Service层写入Data层CalibrationData

【运行阶段】
HAL层(HardwareStatusReader) → EventBus → Service层(TempCompensationService订阅)
                                                   ↓ (达到阈值)
                                         Data层(CalibrationData.查表切换参数)
                                                   ↓
                                         EventBus(CalibrationUpdated事件)
```

**与Algorithm层的关系**:
- **标定阶段**: 通过WorkflowContext调用Algorithm层TempCompensator生成参数表
- **运行阶段**: 只做查表切换，不调用Algorithm层（查表是简单数据操作，无复杂计算）

#### 2.7.11 温度补偿参数表生成（TempCompensator）- 算法层

**功能**: 在标定完成后，根据基准标定参数和补偿算法，预计算生成温度-参数映射表

**位置**: 核心算法层（CPU算法）

**输入**:
- 基准标定参数（标定工作流获得）
- 基准温度（标定时的环境温度）
- 温度补偿模型参数
- 温度范围和步长配置

**输出**:
- 温度-标定参数映射表（存储到CalibrationData）

**预计算流程**:
```
┌─────────────────────────────────────────────────────────────────────┐
│              温度补偿参数表预计算流程                                 │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   输入: 基准标定参数(T0), 补偿模型参数, 温度范围[-10°C, +40°C]       │
│                                                                     │
│   ┌────────────────────────────────────────────────────────────┐   │
│   │  1. 确定温度步长（如每2°C一个参数组）                        │   │
│   │     temperatures = [-10, -8, -6, ..., 38, 40]  // 26个点   │   │
│   └────────────────────────────────────────────────────────────┘   │
│                              ↓                                      │
│   ┌────────────────────────────────────────────────────────────┐   │
│   │  2. 遍历每个温度点，计算补偿后的标定参数                      │   │
│   │     for T in temperatures:                                 │   │
│   │         ΔT = T - T0                                        │   │
│   │         ΔR = f_R(ΔT, params_R)  // 旋转补偿                │   │
│   │         ΔT_vec = f_T(ΔT, params_T)  // 平移补偿            │   │
│   │         R_T = R_基准 * ΔR                                  │   │
│   │         T_T = T_基准 + ΔT_vec                              │   │
│   │         计算立体矫正矩阵(R1, R2, P1, P2, Q)_T              │   │
│   │         存入参数表[T] = {R_T, T_T, 矫正矩阵_T}             │   │
│   └────────────────────────────────────────────────────────────┘   │
│                              ↓                                      │
│   ┌────────────────────────────────────────────────────────────┐   │
│   │  3. 将参数表存储到CalibrationData                           │   │
│   │     tempParamTable: Map<float, CalibrationParams>          │   │
│   └────────────────────────────────────────────────────────────┘   │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘

**优势**:

#### 2.7.12 姿态计算（PoseCalculator）- 算法层

**功能**: 根据图像中的标记点计算扫描仪相对于标定板的姿态

**位置**: 核心算法层（CPU算法）

**输入**:
- 左右相机图像中检测到的标记点2D坐标
- 标定板上标记点的已知3D坐标
- 相机内参

**输出**:
- 扫描仪相对于标定板的旋转矩阵R和平移向量T
- 姿态误差评估（重投影误差）

**算法流程**:
1. 标记点2D-3D对应匹配
2. PnP（Perspective-n-Point）求解初始姿态
3. RANSAC剔除异常点
4. 非线性优化精化姿态

**主要方法**:
- `calculatePose(marker2D, marker3D, intrinsic)`: 计算姿态
- `evaluatePose(pose, markers)`: 评估姿态精度

#### 2.7.13 外参计算（ExtrinsicCalib）- 算法层

**功能**: 根据多组标定姿态计算双目相机的立体外参

**位置**: 核心算法层（CPU算法）

**输入**:
- 多组标定姿态（扫描仪相对于标定板的R, T）
- 各姿态下的标记点2D坐标
- 相机内参

**输出**:
- 左右相机之间的旋转矩阵R和T（立体外参）
- 标定精度评估

**算法流程**:
1. 收集多组姿态下的标记点数据
2. 基于对极几何约束计算初始外参
3. Bundle Adjustment全局优化
4. 计算重投影误差评估精度

**主要方法**:
- `calibrate(poseList, marker2DList)`: 执行外参标定
- `getCalibrationError()`: 获取标定误差

#### 2.7.14 立体矫正计算（StereoRectify）- 算法层

**功能**: 根据内外参计算立体矫正参数

**位置**: 核心算法层（CPU算法）

**输入**:
- 左右相机内参（焦距、主点、畸变系数）
- 立体外参（R, T）
- 图像尺寸

**输出**:
- 左右相机矫正旋转矩阵（R1, R2）
- 左右相机投影矩阵（P1, P2）
- 视差到深度映射矩阵Q
- 有效矫正区域ROI

**算法流程**:
1. 基于Bouguet算法计算矫正旋转
2. 计算投影矩阵使视差最小化
3. 生成视差-深度映射矩阵
4. 计算有效矫正区域

**主要方法**:
- `rectify(intrinsic1, intrinsic2, R, T, imageSize)`: 计算矫正参数
- `getRectifyMaps()`: 生成用于实时矫正的映射表

#### 2.7.15 光平面标定（LightPlaneCalib）- 算法层

**功能**: 标定激光光平面方程参数

**位置**: 核心算法层（CPU算法）

**输入**:
- 多组标定姿态下的激光光条图像
- 对应姿态的相机外参
- 相机内参

**输出**:
- 光平面方程参数（Ax + By + Cz + D = 0）
- 标定精度评估

**算法流程**:
1. 提取各姿态下的激光光条中心点
2. 将光条点反投影到3D空间
3. 使用多姿态数据拟合光平面
4. RANSAC剔除异常点并优化

**主要方法**:
- `calibrate(images, extrinsics, intrinsic)`: 执行光平面标定
- `getPlaneParams()`: 获取光平面参数
- `getCalibrationError()`: 获取标定误差

#### 2.7.16 单帧判断模块（FrameDecisionModule）- 数据层

**功能**: 判断当前帧激光点云是否需要保存到原始帧存储

**位置**: 数据层

**判断策略**:
- 基于点云质量评估（点数、分布均匀性）
- 基于运动检测（帧间变换矩阵变化）
- 基于重叠度检测（与已有帧的重叠比例）
- 可配置保存策略（全部保存/智能保存/关键帧保存）

**输入**:
- 当前帧激光点云
- 当前帧变换矩阵
- 全局点云状态

**输出**:
- 是否保存该帧（true/false）
- 保存原因（用于调试）

**主要方法**:
- `evaluate(frameData, transform)`: 评估是否需要保存
- `setStrategy(strategy)`: 设置保存策略
- `getStatistics()`: 获取保存统计信息

#### 2.7.19 GPU内存池（GpuMemoryPool）- 数据层

**功能**: 管理GPU显存的分配、复用和释放，支持零拷贝数据传输

**位置**: 数据层

**设计目的**:
- 避免频繁的cudaMalloc/cudaFree调用（开销大）
- 支持流水线中多帧数据的并行处理
- 统一管理CPU-GPU数据传输

**显存预算分析**:

```
┌─────────────────────────────────────────────────────────────────────┐
│                        显存预算分析                                  │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  【单帧数据大小】                                                    │
│  · 原始图像: 1800 × 1200 × 1 byte = 2.16 MB (Mono8)                │
│  · 双目图像: 2.16 MB × 2 = 4.32 MB                                 │
│  · 预处理图像: 4.32 MB (原地操作或复用)                             │
│  · 激光点云: 100,000点 × (12+4) byte = 1.6 MB (xyz+intensity)      │
│  · 标记点: 100点 × 12 byte = 1.2 KB (忽略不计)                     │
│  · 单帧合计: ≈ 6 MB                                                 │
│                                                                     │
│  【环形缓冲区(3帧)】                                                 │
│  · 3帧 × 6 MB = 18 MB                                               │
│                                                                     │
│  【全局点云缓冲】                                                    │
│  · 假设1000万点: 10,000,000 × 16 byte = 160 MB                     │
│  · 体素下采样后: ≈ 50 MB                                            │
│                                                                     │
│  【临时工作空间】                                                    │
│  · 中间计算缓冲: ≈ 20 MB                                            │
│                                                                     │
│  【总预算】                                                          │
│  · 最低需求: 18 + 50 + 20 = 88 MB                                   │
│  · 推荐配置: 512 MB 显存预留                                        │
│  · 典型GPU: RTX 3060 (12GB) / Orin (32GB共享) 充足                 │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**接口定义**:
```cpp
class GpuMemoryPool {
public:

    void initialize(size_t poolSize);              // 初始化内存池
    void cleanup();                                 // 清理所有资源

    struct ImageBuffer {
        uint8_t* d_left;           // 左相机图像GPU指针
        uint8_t* d_right;          // 右相机图像GPU指针
        int width, height;
        cudaStream_t stream;       // 关联的CUDA流
    };

    void releaseImageBuffer(ImageBuffer* buf);     // 释放图像缓冲

    struct PointCloudBuffer {
        float* d_points;           // 点坐标 (N×3)
        float* d_intensity;        // 强度值 (N×1)
        int capacity;              // 最大容量
        int count;                 // 当前点数
    };
    PointCloudBuffer* acquirePointCloudBuffer(int maxPoints);
    void releasePointCloudBuffer(PointCloudBuffer* buf);
    
    // 临时工作空间
    void* allocTempWorkspace(size_t size);         // 分配临时空间
    void freeTempWorkspace(void* ptr);             // 释放临时空间
    
    // 数据传输（异步）
    void copyToDeviceAsync(void* dst, const void* src, 
                           size_t size, cudaStream_t stream);
    void copyToHostAsync(void* dst, const void* src, 
                         size_t size, cudaStream_t stream);
    
    // 统计信息
    size_t getUsedMemory() const;
    size_t getTotalMemory() const;
};

#### 2.7.20 DataContext数据上下文 - 工作流层

**功能**: 封装对Data层的所有读写操作，降低工作流与Data层的耦合

**位置**: 工作流层

## 3. 可配置处理流水线

### 3.1 流水线设计理念

采用**可组合Stage架构**，通过Pipeline框架和可复用的Stage模块，灵活配置不同工作流的处理路径。

**适用范围**:
- ✅ **PipelineWorkflow**: 标定、扫描标记点、扫描点云（实时帧处理，多线程流水线）
- ✅ **BatchWorkflow**: 后处理（离线批量处理，单线程）
- ✅ **SyncWorkflow**: 文件IO（同步阻塞操作）

#### 3.1.1 Pipeline框架架构

### 3.2 流水线线程架构

**扫描点云工作流**采用**多线程流水线模型**，将处理流程分解为5个专用线程：

| 线程名 | 职责 | 执行设备 | 同步机制 |
|--------|------|----------|----------|
| **CaptureThread** | 从两个相机同步获取图像帧，与下位机通信获取温度、按键等信息 | CPU | 环形缓冲区+信号量 |
| **PreprocessThread** | CUDA Stream 0执行GPU预处理（去噪、对比度增强、ROI提取） | GPU | CUDA Event |
| **MarkerThread** | 从预处理图像提取标记点，去畸变，左右匹配，视差计算，三维重建 | CPU | 双缓冲+事件 |
| **LaserThread** | CUDA Stream 1提取激光中心，去畸变，极线插值匹配，三维重建 | GPU+CPU | CUDA Event |
| **FusionThread** | 标记点配准计算变换矩阵，激光点坐标转换，实时下采样，更新全局点云 | CPU | 互斥锁 |

> **注**: RenderThread由UI层管理，不在此流水线架构内。详见5.1节点云视图说明。

**线程数据流**:
```
CaptureThread ──[环形缓冲区]──→ PreprocessThread
                                      │
                    ┌─────────────────┴─────────────────┐
                    ↓                                   ↓
             MarkerThread                        LaserThread
                    │                                   │
                    └─────────────→ FusionThread ←──────┘
                                          │
                                          ↓
                               Data层: PointCloudBuffer
                                          │
                                          ↓ (UI层直接读取)
                                   RenderThread (UI层管理)
```

### 3.3 同步机制（扫描点云工作流）

- **采集到预处理**: 使用环形缓冲区配合信号量，采集线程写入帧数据后触发信号量，预处理线程等待信号量后读取。
- **预处理到处理**: 使用双缓冲机制，预处理完成时通过事件通知处理线程。
- **CUDA操作同步**: 使用CUDA Event在各Stream间同步，确保核函数执行顺序正确。

### 3.3 性能目标（扫描点云工作流）

| 线程 | 处理时间目标 | 说明 |
|------|-------------|------|
| 采集 | <1ms | USB3.2带宽充足 |
| GPU预处理 | 2-3ms | 1800x1200图像 |
| 标记点处理 | 1-2ms | 通常少于20个标记点 |
| 激光点处理 | 3-5ms | 5-10万点 |
| 融合下采样 | 2-3ms | 增量更新 |

**流水线时序分析**:

```
【帧间隔 vs 首帧延迟】

时间轴 (ms):  0    5    10   15   20   25   30   35   40   45   50
             │    │    │    │    │    │    │    │    │    │    │
Capture:     [F1] [F2] [F3] [F4] [F5] [F6] ...
             │    │    │    │    │    │    │
Preprocess:  ───►[F1] [F2] [F3] [F4] [F5] ...
             │    │    │    │    │    │
Marker:      ─────────►[F1] [F2] [F3] ...
             │    │    │    │    │
Laser:       ─────────►[F1──][F2──][F3──] ...
             │    │    │    │    │
Fusion:      ───────────────►[F1][F2][F3] ...
             │    │    │    │    │
             ▼    ▼    ▼    ▼    ▼    ▼    ▼    ▼    ▼    ▼    ▼

关键指标:
┌─────────────────────────────────────────────────────────────────────┐
│ 【帧间隔 (Frame Interval)】                                          │
│ · 定义: 相邻两帧从采集到融合完成的时间差                             │
│ · 计算: max(Capture, Preprocess, Marker, Laser, Fusion) ≈ 5-6ms    │
│ · 目标: 1000ms / 180fps = 5.56ms/帧                                 │
│ · 结论: 满足180fps连续输出要求 ✓                                    │
├─────────────────────────────────────────────────────────────────────┤
│ 【首帧延迟 (First Frame Latency)】                                   │
│ · 定义: 第一帧从采集到融合完成的总时间                               │
│ · 计算: Capture + Preprocess + max(Marker,Laser) + Fusion          │
│ · 估算: 1ms + 3ms + 5ms + 3ms = 12ms                               │
│ · 实际: 考虑线程唤醒和同步开销，约15-20ms                           │
│ · 结论: 远低于50-100ms要求 ✓                                        │
├─────────────────────────────────────────────────────────────────────┤
│ 【系统响应延迟 (System Response Latency)】                           │
│ · 定义: 从物体移动到用户看到点云变化的延迟                           │
│ · 组成: 采集延迟 + 处理延迟 + 渲染延迟                              │
│ · 估算: 5.56ms + 15ms + 16.67ms(60fps渲染) ≈ 37ms                  │
│ · 结论: 满足50-100ms要求 ✓                                          │
└─────────────────────────────────────────────────────────────────────┘
```

**性能瓶颈分析**:

| 阶段 | 潜在瓶颈 | 优化策略 |
|------|---------|---------|
| 采集 | USB带宽、驱动延迟 | 零拷贝、环形缓冲 |
| GPU预处理 | 核函数效率、显存带宽 | 共享内存、合并访问 |
| 标记点处理 | 特征检测算法 | OpenCV优化、SIMD |
| 激光点处理 | 点数过多 | GPU并行、空间索引 |
| 融合 | 全局点云遍历 | 增量更新、体素过滤 |

总延迟控制在50-100ms内，满足180fps连续输出要求。

### 3.4 后处理工作流（PostProcessWorkflow）

后处理工作流采用**BatchWorkflow模式**，实现IWorkflow接口，进行离线批量处理。

**设计原因**:
- 后处理是对已采集数据的批量处理，非实时帧处理
- 处理步骤是同步阻塞的，无需流水线并行
- 与实时扫描工作流的执行模式不同，但仍需统一的生命周期管理

**与PipelineWorkflow的区别**:
| 特性 | PipelineWorkflow | BatchWorkflow |
|------|------------------|---------------|
| 执行模式 | 多线程流水线 | 单线程串行 |
| 数据来源 | 实时帧采集 | 已存储的原始帧 |
| 并行性 | Stage可并行 | 步骤串行执行 |
| 适用场景 | 标定/扫描 | 后处理 |

**处理流程**:

7. **光顺处理**: GPU加速的光顺滤波
8. **导出文件**: 通过DataContext输出STL/PLY/OBJ/ASC/TXT等格式

**内存监控和保护**:

```cpp
class PostProcessWorkflow : public IWorkflow {
private:
    size_t memoryBudget_;  // 内存预算，默认4GB
    
    bool checkMemoryAvailable(size_t required) {
        size_t available = getSystemAvailableMemory();
        return available > required + 500_MB;  // 预留500MB
    }
    
    void processInBlocks() {
        const int blockSize = 500;  // 每块500帧
        for (int i = 0; i < totalFrames_; i += blockSize) {
            // 检查内存
            if (!checkMemoryAvailable(blockSize * frameSize_)) {
                // 内存不足，降低块大小或暂停
                handleMemoryPressure();
            }
            
            // 加载块
            auto frames = dataContext_.loadRawFrames(i, blockSize);
            
            // 处理
            processBlock(frames);
            
            // 释放
            frames.clear();
            
            // 更新进度
            updateProgress(i, totalFrames_);
            
            // 检查暂停请求
            if (pauseRequested_) {
                waitForResume();
            }
        }
    }
};
```

## 4. 核心数据结构

### 4.1 帧数据结构

**结构定义**:
```
FrameData {
    // 帧头信息
    uint64_t frameId;           // 帧ID（递增序号）
    uint64_t timestamp;         // 时间戳（微秒级）
    
    // 相机1数据
    uint8_t* imageLeft;         // 左相机图像指针（Mono8格式，指向共享内存）
    int imageWidth;             // 图像宽度（1800）
    int imageHeight;            // 图像高度（1200）
    float camera1Temp;          // 相机1温度
    float camera1FrameRate;     // 相机1帧率
    
    // 相机2数据
    uint8_t* imageRight;        // 右相机图像指针（Mono8格式，指向共享内存）
    float camera2Temp;          // 相机2温度
    float camera2FrameRate;     // 相机2帧率
}
```

**图像格式**: Mono8（8位灰度图像）

**内存管理**: 图像通过指针共享而非拷贝，减少内存开销。图像数据存储在共享内存池的环形缓冲区中。

**帧ID规则**: 从0开始递增，每次采集新帧时自动加1

**时间戳来源**: 来自相机帧头信息，微秒级精度

### 4.2 标记点结构

2D标记点包含像素坐标和置信度；3D标记点包含三维坐标、所属帧ID、跨帧匹配用的标记点ID。标记点ID用于多帧间的标记点匹配追踪。

### 4.3 激光点云结构

单个激光点包含三维坐标和反射强度。每帧点云包含帧ID、点向量（5-10万点）、该帧的变换矩阵。变换矩阵由标记点配准计算得出。

### 4.4 全局点云缓冲

维护全局融合后的激光点云和标记点集合，使用互斥锁保护并发访问。提供添加帧、下采样、获取显示数据等接口。下采样基于体素网格，根据预设分辨率合并邻近点。

### 4.5 标定参数

分为四部分：相机内参（焦距、主点、畸变系数）、立体外参（旋转矩阵、平移向量、左右相机立体校正矩阵）、光平面参数（光平面方程系数）、温度补偿参数表（温度-标定参数映射表）。内参在标定后固定，外参、光平面和温度补偿参数表可通过标定工作流生成。

**温度补偿参数表结构**:
```
CalibrationData {
    // 基础标定参数（始终保存）
    IntrinsicParams intrinsic1, intrinsic2;  // 相机内参
    CalibrationParams baseParams;             // 基准标定参数（标定温度下）
    LightPlaneParams lightPlane;              // 光平面参数
    float baseTemp;                           // 标定时的基准温度
    
    // 温度补偿参数表（预计算生成）
    TempParamTable tempParamTable {
        float tempStep;           // 温度步长（默认2.0°C）
        float tempMin;            // 最低温度（默认-10°C）
        float tempMax;            // 最高温度（默认+40°C）
        map<float, CalibrationParams> table;  // 温度→参数映射
    }
    
    // 当前生效参数（运行时切换）
    CalibrationParams activeParams;  // 当前使用的标定参数
    float activeTemp;                // 当前参数对应的温度
}
```

运行时由Service层TempCompensationService监控温度变化，当温差超过阈值时，从tempParamTable中查找并切换activeParams。

### 4.6 系统状态与故障信息

系统状态枚举包括：空闲、标定中、扫描标记点、扫描点云、后处理中、错误。故障信息包含故障源（相机1/2、下位机、系统）、错误码、消息、时间戳。

## 5. 硬件抽象层(HAL)

### 5.1 设计目标

HAL层将硬件相关操作抽象为统一接口，上层模块通过接口调用，不直接依赖具体硬件实现。Windows和Jetson平台的差异被封装在各自的实现文件中，编译时通过宏选择。

### 5.2 相机接口（ICamera1/ICamera2）

**通讯方式**: 相机通过下位机中继与上位机通讯，每个相机有独立端口
- 相机1端口: USB3.2 GEN1（通过下位机中继）
- 相机2端口: USB3.2 GEN1（通过下位机中继）

**注意**: 相机的硬件触发由IMCU接口控制（通过下位机I/O触发），ICamera接口不负责触发控制

**功能**:
- 参数配置（11个预留指令）
- 读取温度和帧率
- 帧数据接收
- 故障回调设置

**支持相机**: 
- 相机1: 大恒VE2S-301-125U3M-S (1800×1200, 180fps)
- 相机2: 大恒VE2S-301-125U3M-S (1800×1200, 180fps)

### 5.3 下位机接口（IMCU）

下位机控制接口，负责相机硬件触发、外设控制和同步采集。

**通讯方式**: USB3.2 GEN2（控制端口）

**功能模块**:
- **连接管理**: 连接/断开、连接状态检测
- **相机硬件触发**: 
  - 控制相机1/相机2的I/O硬触发信号
  - 实现双目同步采集的核心机制
- **采集控制**: 启动/停止同步采集（帧率、激光亮度、补光灯亮度）
- **激光器控制**: 亮度设置、开关控制（17/25条440-450nm蓝色激光线，Ⅱ级人眼安全）
- **补光灯控制**: 左右补光灯独立亮度控制（2个450nm LED环形补光灯）
- **指示灯控制**: 红色=通讯故障、绿色=通讯正常
- **状态读取**: 按键状态、骨架温度传感器
- **预留指令**: 15个自定义指令
- **故障回调**: 通讯故障通知

**同步触发机制**:
- IMCU发送I/O硬触发信号同步触发相机1、相机2
- 同时控制激光器、补光灯与相机同步
- 支持180fps帧率
- 相机通过下位机I/O触发实现微秒级同步

### 5.4 CUDA上下文接口

提供初始化/清理、GPU内存分配/释放、主机到GPU/GPU到主机数据拷贝、CUDA Stream创建/销毁/同步、获取计算能力和可用显存等功能。

### 5.5 平台接口

提供获取平台类型（Windows或Jetson）、CUDA架构字符串（Windows为86/89/90，Jetson为87）、GPU数量等信息。

### 5.6 编译时多态实现

通过预处理器宏区分平台，在工厂类中根据宏定义返回对应平台的实现类实例。这种方式在编译时确定具体类型，无运行时虚函数开销，适合对性能敏感的实时系统。

## 6. 工作流设计

### 6.1 状态机与工作流生命周期

**系统状态转换规则**:
- 空闲状态可进入标定、扫描标记点、扫描点云
- 标定完成后返回空闲
- 扫描标记点可切换到扫描点云
- 扫描点云可进入后处理或返回空闲
- 后处理完成后返回空闲
- 任意状态发生故障进入错误状态，故障恢复后返回空闲

**工作流生命周期管理**:

状态机通过IWorkflow接口管理工作流的生命周期：

**状态机与工作流的交互**:
```cpp
class StateMachine {
private:
    std::shared_ptr<IWorkflow> currentWorkflow_;
    
public:
    void startWorkflow(WorkflowType type) {
        // 1. 创建对应工作流
        currentWorkflow_ = workflowFactory_.create(type, dataContext_);
        
        // 2. 设置回调
        currentWorkflow_->setCompleteCallback([this](bool success) {
            onWorkflowComplete(success);
        });
        
        // 3. 执行工作流
        currentWorkflow_->execute();
        
        // 4. 发布状态变化事件
        eventBus_.publish(StateChangedEvent{});
    }
    
    void stopCurrentWorkflow() {
        if (currentWorkflow_) {
            currentWorkflow_->stop();
            currentWorkflow_.reset();
        }
    }
    
    void pauseCurrentWorkflow() {
        if (currentWorkflow_) {
            currentWorkflow_->pause();
        }
    }
};
```

### 6.2 标定工作流

输入初始内参、外参、立体矫正参数。工作流程：加载初始标定参数，在界面显示扫描仪和标定板的指引姿态，实时采集并计算当前姿态，当姿态在指引范围内时保存该姿态图像，全部姿态采集完成后计算外参、立体校正参数和光平面，同时在多个温度点采集数据以获取温度补偿模型参数，最后在界面显示标定精度。注意内参沿用原始值不重新计算。

**标定流程详解**:
```
┌─────────────────────────────────────────────────────────────────────┐
│                        标定工作流流程                                │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  1. 初始化                                                          │
│     └── 加载初始内参、外参、立体矫正参数                            │
│                                                                     │
│  2. 姿态采集（循环，采集多组姿态）                                   │
│     ┌────────────┐    ┌────────────┐    ┌────────────┐            │
│     │ 采集图像   │ →  │ 标记点提取 │ →  │ PoseCalc   │            │
│     │            │    │            │    │ 计算姿态   │            │
│     └────────────┘    └────────────┘    └─────┬──────┘            │
│                                              ↓                     │
│                                    ┌────────────────────┐          │
│                                    │ 姿态在指引范围内?  │          │
│                                    └─────────┬──────────┘          │
│                                              │ 是                  │
│                                              ↓                     │
│                                    ┌────────────────────┐          │
│                                    │ 保存该姿态数据     │          │
│                                    └────────────────────┘          │
│                                                                     │
│  3. 参数计算（所有姿态采集完成后）                                   │
│     ┌────────────────┐    ┌────────────────┐    ┌────────────────┐│
│     │ ExtrinsicCalib │ →  │ StereoRectify  │ →  │ LightPlaneCalib││
│     │ 计算立体外参   │    │ 计算立体矫正   │    │ 标定光平面     ││
│     └────────────────┘    └────────────────┘    └────────────────┘│
│                                                                     │
│  4. 温度补偿参数表生成                                               │
│     └── 调用TempCompensator生成温度-参数映射表                      │
│                                                                     │
│  5. 存储                                                            │
│     └── 保存到CalibrationData并持久化                               │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**各步骤使用的算法层模块**:
| 步骤 | 算法模块 | 说明 |
|------|---------|------|
| 姿态计算 | PoseCalculator | PnP求解扫描仪相对标定板的姿态 |
| 外参计算 | ExtrinsicCalib | 多姿态Bundle Adjustment优化 |
| 立体矫正 | StereoRectify | Bouguet算法计算矫正参数 |
| 光平面标定 | LightPlaneCalib | 多姿态激光点拟合光平面 |
| 温度表生成 | TempCompensator | 预计算温度-参数映射表 |

**温度补偿参数表生成**（标定完成后自动执行）:
1. **记录标定温度**: 标定完成时，记录当前环境温度作为基准温度T0
2. **获取补偿模型**: 通过多温度点标定或预设模型，获取温度-外参变化模型参数
3. **预计算参数表**: 调用Algorithm层TempCompensator生成温度-标定参数映射表
   - 温度范围: 根据工作环境配置（如-10°C ~ +40°C）
   - 温度步长: 可配置（如每2°C一个参数组）
   - 计算内容: 每个温度点的外参、立体矫正矩阵
4. **存储到Data层CalibrationData**: 将参数表持久化保存，供运行时查表使用

```
标定工作流完成后:
┌─────────────┐     ┌──────────────────┐     ┌─────────────────────┐
│ 标定参数    │  +  │ 基准温度 T0      │  →  │ 温度补偿参数表       │
│ (R,T,矫正)  │     │ 补偿模型参数     │     │ (-10°C ~ +40°C)     │
└─────────────┘     └──────────────────┘     └─────────────────────┘
```

### 6.3 扫描标记点工作流

**类型**: PipelineWorkflow（实现IWorkflow接口）

每帧处理流程：通过WorkflowContext读取图像帧，传入GPU预处理，CPU提取标记点中心，CPU执行去畸变，CPU进行左右相机匹配和视差计算，CPU三维重建标记点，CPU配准到全局标记点集合。全部采集完成后执行全局标记点配准优化，结果通过WorkflowContext写入Data层。

### 6.4 扫描点云工作流

**类型**: PipelineWorkflow（实现IWorkflow接口）

每帧处理分为两条并行路径：

**路径A(CPU)**: 提取标记点中心 → 去畸变 → 匹配和视差计算 → 三维重建标记点 → 配准并计算该帧的变换矩阵

**路径B(GPU→CPU)**: 提取激光中心点 → 去畸变 → 基于极线插值匹配 → 三维重建激光点 → 将结果读入CPU内存

**汇合后**: 应用变换矩阵对激光点做坐标转换 → 实时下采样（当前帧与全局点云合并）→ 通过WorkflowContext更新全局点云 → 判断该帧是否保存（通过WorkflowContext保留未做变换前的原始数据供后处理使用）

### 6.5 后处理工作流

**类型**: BatchWorkflow（实现IWorkflow接口）

流程：通过WorkflowContext读取未做全局配准前的每帧标记点和激光点 → 全局融合并重新计算每帧的精确变换矩阵 → 对激光点做坐标转换 → 全局下采样（根据预设密度）→ 封装三角面（使用CGAL/PCL）→ 补洞（标记点位置及其他孔洞）→ 光顺处理（GPU加速）→ 通过WorkflowContext导出文件（STL、PLY、OBJ、ASC、TXT等格式）。

**支持进度回调和暂停/恢复**。

### 7.9 渲染线程与数据更新同步机制

**接口设计**:

```cpp
class PointCloudBuffer {
private:
    struct Buffer {
        std::vector<Point3f> points;
        std::vector<float> intensities;
        std::atomic<bool> isWriting{false};
        std::atomic<bool> isReading{false};
        std::atomic<bool> isReady{false};
    };
    
    Buffer buffers_[3];  // 三缓冲
    std::atomic<int> writeIndex_{0};
    std::atomic<int> readIndex_{2};
    
public:
    // FusionThread调用
    WriteLock acquireWriteBuffer() {
        int idx = writeIndex_.load();
        buffers_[idx].isWriting = true;
        return {&buffers_[idx], idx};
    }
    
    void releaseWriteBuffer(int idx, bool requestSwap = true) {
        buffers_[idx].isWriting = false;
        buffers_[idx].isReady = true;
        if (requestSwap) {
            trySwapBuffers();
        }
    }
    
    // RenderThread调用
    ReadLock acquireReadBuffer() {
        int idx = readIndex_.load();
        if (!buffers_[idx].isReady) {
            return {nullptr, -1};  // 无新数据
        }
        buffers_[idx].isReading = true;
        return {&buffers_[idx], idx};
    }
    
    void releaseReadBuffer(int idx) {
        buffers_[idx].isReading = false;
        buffers_[idx].isReady = false;  // 标记为已消费
    }
    
private:
    void trySwapBuffers() {
        // 无锁交换逻辑
        // 找到Ready且不在Reading的缓冲区
        // 与当前ReadBuffer交换
    }
};
```

**OSG渲染优化**:

```cpp
class PointCloudView : public osgViewer::View {
private:
    osg::ref_ptr<osg::Geode> pointGeode_;
    osg::ref_ptr<osg::Geometry> pointGeometry_;
    osg::ref_ptr<osg::Vec3Array> vertices_;
    osg::ref_ptr<osg::Vec4Array> colors_;
    
    PointCloudBuffer& buffer_;
    std::atomic<bool> running_{true};
    
public:
    void startRendering() {
        // OSG渲染线程
        while (running_) {
            // 获取读缓冲
            auto readLock = buffer_.acquireReadBuffer();
            if (readLock.buffer) {
                // 更新OSG顶点数据
                updateGeometry(readLock.buffer);
                
                // 释放缓冲
                buffer_.releaseReadBuffer(readLock.index);
            }
            
            // 触发渲染帧
            frame();
            
            // 控制帧率 (60fps)
            std::this_thread::sleep_for(16ms);
        }
    }
    
private:
    void updateGeometry(const Buffer* buf) {
        // 使用OSG的动态数据更新
        // 避免频繁的内存分配
        vertices_->resize(buf->points.size());
        memcpy(vertices_->getDataPointer(), 
               buf->points.data(), 
               buf->points.size() * sizeof(Point3f));
        
        pointGeometry_->setVertexArray(vertices_);
        pointGeometry_->dirtyBound();
    }
};
```
