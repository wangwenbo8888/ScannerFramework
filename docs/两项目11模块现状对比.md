## 总结

### framework 领先的（4项）
1. **文件管理** — 完整 PLY/STL/OBJ/PCD 导入导出 + 进度框
2. **编辑** — 有套索/删除/撤销基础功能
3. **标定UI/3D显示** — CalibDialog + CalibDisplay 更完整
4. **应用可用性** — 有可运行的 GUI（MainWindow + OSGWidget）

### K2 领先的（4项）
1. **渲染** — CUDA-GL 零拷贝实时渲染
2. **算子完整性** — 多 optical_flow_fuse + 完整温度补偿链 + ctest覆盖
3. **模块覆盖** — 9个模块有代码（vs framework 7个）
4. **并行流水线设计** — 文档设计完整

### 共同短板（5项）
后处理编排、会话管理逻辑、扫描并行流水线、可观测性、安装部署——**两个项目都未实现**。

### 重构后的变化

framework 经过3步模块化重构后：
- 模块目录**命名正确**、**7个模块有代码**（原来只有2个）
- app/ 从 10cpp **缩减到 3cpp**（仅入口）
- 架构组织从"单体app"变为"模块+共享层"
- 与 K2 的架构组织差距**大幅缩小**（原来"模块化程度低"，现在"中等"）

### 一句话结论

**framework = "能跑的应用 + 中等模块化"**（UI/IO/渲染/编辑可运行，7个模块有代码，共享层在framework/）。
**K2 = "完整的架构 + 全面的算子"**（9个模块有代码，CUDA-GL渲染，算子全，并行设计完整）。
**两者互补**：framework 缺 K2 的算子+CUDA渲染，K2 缺 framework 的可用业务代码。
